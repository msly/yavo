# Zhunsheng（准绳）规划 v0.2：面向 agent 的无 GC 系统语言

Nov 10, 2026 · @ali tea

## v0.2 变更

v0.2 吸收了一份外部技术评审，并定下名字：语言叫 **Zhunsheng（准绳）**，命令行是 `zhun`，源文件扩展名是 `.zhun`。

名字取自木匠弹线用的墨绳，《荀子》说“木受绳则直”：用所有权规则和机器验证，让 AI 写的代码取直。2026-11-10 的网络检索没有发现同名的编程语言或开发工具；Tenon、Sunmao、Guiju、Taut 因已被占用、Ailow 因与 Ailoy 太近而放弃。正式发布前仍需做商标核查。

主要改动：

- 视图规则从“不能进集合”改为“不能逃逸”：局部的视图集合（如 `Vec[str]`）允许存在，零拷贝解析不再需要复制字符串。
- 集合和 Arena 的读取统一返回借用，不再隐式复制或移出。
- 导出函数返回视图时必须在签名里写明来源（`-> str of s`），避免改函数体引发远处报错。
- 接口值放进集合要显式装箱；`Arc[T]` 能否跨线程要看 `T`；Arena 的 Id 带上 Arena 身份。
- “零隐式分配”改为“语法不隐式分配，可能分配的标准库操作有成本说明”。
- panic 直接终止进程，测试运行器把每个测试放进单独的子进程。
- Windows 进入第一阶段并上 CI；v1 不写 WASI 平台层。
- 正式对照组改为“Rust 1.99 加 agent 工具层”，晋级要同时过正确性和成本两道门槛。
- 产品目标加上结构化验证报告。

## 定位与目标

Zhunsheng 是面向 agent 的原生系统语言：无 GC，靠所有权检查保证内存安全，性能接近 C，三个桌面平台从第一天起都能编译和运行。

产品目标：给定程序规格，agent 能以最低成本交付一个经过机器验证、可复现构建、满足目标平台约束的原生程序；人只批准规格和验收标准，不逐行读代码。

硬性要求有四条：

1. 无 GC。
2. 性能接近 C。
3. 跨平台编译方便，第一阶段就包含 Windows。
4. 使用者是 agent：代码由 AI 生成，人只写规格和看结果。

设计原则：

- **迭代轮数比打字成本重要。** 样板代码可以多，歧义不能多。
- **没人读代码，正确性靠机器验证。** 测试、审计和验证报告要内置。
- **没有训练数据。** 模型只能靠一页速查卡和编译器的反馈来学。
- **检查只看单个函数和签名。** 改一处不会在远处引发错误。
- **语法不隐藏行为。** 没有隐式拷贝、隐式控制流，普通语法不引入堆分配；可能分配的标准库操作有成本说明，可以用命令查询。

已定的决定：

| 项目 | 决定 |
| --- | --- |
| 名字 | Zhunsheng（准绳），命令 `zhun`，扩展名 `.zhun` |
| 许可证 | Apache-2.0；运行时附第三方版权声明清单 |
| 编译器实现 | Rust，允许少量经过审计的依赖 |
| 第一代后端 | 生成 C |
| 交叉编译 | 固定版本的 Zig |
| Windows 目标 | `x86_64-windows-gnu`；MSVC ABI 放到以后 |
| 并发 | OS 线程、`scope`、channel |
| panic | 终止进程，不展开栈 |

## 依据

本规划是有依据的假设，不是定论：数据来自一个 agent、10 道 30 到 150 行的小题，在一台 Linux x86-64 沙箱里测得。

| 测量项 | Gojo（nightly 0.0.1-20261109） | Rust 1.75 |
| --- | --- | --- |
| 10 道题最终通过 | 10/10 | 10/10 |
| 一次通过 | 7/10 | 10/10 |
| 总尝试次数 | 14 | 10 |
| 编译通过后测试失败 | 0 次 | 0 次 |
| 编译耗时中位数 | 109 ms | 260 ms（波动大） |
| 二进制，strip 后中位数 | 约 200 KB | 约 390 到 430 KB |
| 项目目录内的中间产物 | 无 | cargo 零依赖时 13 到 16 MB |
| 带一个 regex 依赖时的产物 | 缓存多一个二进制大小的文件 | `target/` 50 到 104 MB |
| 工具链体积 | 编译器 4.7 MB | 约 294 MB |

Gojo 的 4 次失败全是编译失败：3 次来自所有权和视图模型，1 次来自“未使用变量即报错”。

关于这些数字的三点说明：

- Rust 是 apt 打包的版本，标准库自带调试信息，未 strip 的二进制有 13 MB，所以只比较 strip 后的大小。
- 每题先写 Gojo 后写 Rust，Rust 的一次通过率因此偏高；写题的 agent 对 Rust 和 Go 也有很强的先验。
- token 消耗没有测到，性能没有比较。

Windows 移植的测量：Gojo 生成的 C 可直接为 Windows 编译（0 个错误），但运行时拼成一个单元后有 464 个错误、15 个缺失头文件，集中在调度器、网络、子进程和内存映射。

v0.2 补充的三点：

- **Rust 基线已过时。** 试点用的是 1.75，当前稳定版是 1.99.1（2026 年 10 月 15 日发布）。正式实验要用 rustup 装的 1.99 系列重测。
- **“项目目录零产物”不是语言本身的优势。** Rust 用 `CARGO_TARGET_DIR` 也能把产物移出项目目录，但总量不变；真正可比的是“每次构建新增多少字节”，差异主要来自调试信息和依赖编译。
- **更正对 Gojo 的描述。** Gojo 允许局部的视图集合（`Vec[str]`、`Map[str, int]`）和 `view struct`，返回视图可以写 `-> str of a`；它禁止的是视图进入普通字段、`Box`、接口值和逃逸的闭包。v0.1 的速查卡比 Gojo 还严，而且与自己的 `fields()` 用法矛盾，v0.2 已改正。

## 取舍

只拿 Gojo 被实测验证过的优点，把它的短板从设计上避开。

| 做法 | 决定 | 理由 |
| --- | --- | --- |
| 无生命周期标注、单函数可检查的所有权模型 | 借鉴 | 小题上没有把 agent 卡死，错误集中在少数几类 |
| 局部视图集合（`Vec[str]`）、返回视图写明来源（`-> str of s`） | 借鉴（v0.2 新增） | 零拷贝解析不用复制字符串，视图又不会逃逸 |
| `?T` 取消 nil，`T ! E` 加 `try`/`catch` | 借鉴 | 编译通过的程序全部一次通过测试 |
| 编译成 C，生成代码只依赖一个小头文件 | 借鉴 | 生成的 C 可直接为 Windows 编译 |
| 用 `__builtin_*_overflow` 检查溢出，以 `-fwrapv` 编译 | 借鉴（v0.2 新增） | C 后端不会因有符号溢出产生未定义行为 |
| 编译约 100 ms、二进制约 200 KB、项目零产物 | 借鉴 | 实测数据 |
| 缓存保留最近 64 个二进制 | 改 | 64 个大程序可能占数 GB；改为按字节上限、最近最少使用淘汰 |
| 内置测试、种子可重放、`unsafe` 审计、从类型推导能否跨线程 | 借鉴 | 没人读代码时，这些是主要防线 |
| M:N 调度器、手写汇编、epoll | 不要 | Windows 移植的 464 个错误主要来自这里 |
| 借用持续到词法块结束 | 改 | T04 因此多花一次迭代，改为到最后一次使用为止 |
| 提示用 `.clone()` 修“移出 Box 字段” | 改 | 合法但会深拷贝，应直接建议 `take` |
| 未使用变量是编译错误 | 改 | 浪费一次编译往返，降为警告并可自动修复 |
| HTTP、TLS、YAML 进标准库核心 | 不要 | 推高实现和移植成本，放到包里 |
| 仓库没有许可证文件 | 避开 | 从第一天就用 Apache-2.0 |

## 语言设计

语法贴近 Rust 和 Go 的混合，让模型已有的知识能迁移；具体写法见“速查卡”标签页。v0.2 的改动集中在内存模型。

**语法**

- 一件事只有一种写法，官方格式化工具只有一种风格。
- 没有宏、运算符重载、隐式转换。
- 声明顺序无关，不需要前向声明或头文件；`pub` 标记从包导出的函数和类型。
- 函数边界写显式类型，函数内可以推导。

**类型**

- 结构体、带数据的枚举、接口、元组；泛型用单态化实现，可以用接口约束。
- `?T` 表示可能缺失，`T ! E` 表示可能失败，两者都必须处理。
- 接口值要放进集合或字段时显式装箱：`Vec[Box[Named]]`，不在背后分配。

**内存模型**

- 值默认 move；参数有三种模式：借用（默认）、`inout`（可变借用，调用处写 `&`）、`sink`（移入）。
- 视图包括 `str`、`[]T`、只读借用 `&T`、可变借用 `&inout T`，以及由视图组成的局部集合（如 `Vec[str]`）。视图可以做局部变量、参数和返回值，不能进入普通字段、`Box`、接口值或逃逸的闭包。
- 返回视图时，导出函数必须在签名里写明来源，例如 `pub fn first(s: str) -> str of s`；包内私有函数可以省略，由编译器推断。这样改函数体不会让包外的调用方报错。
- 借用持续到最后一次使用为止；借用期间，来源不能被修改或移动。
- `if let`、`for`、`match` 的绑定跟随来源的可变性：来源是 `var` 或 `inout` 时可以通过绑定修改，否则只读。
- 集合和 Arena 的读取返回借用：`m.get(k)` 得到 `?&V`，`m.getMut(k)` 得到 `?&inout V`；只有可拷贝的类型才能用 `m.getOr(k, 默认值)` 直接拿到值。不隐式复制，也不移出。
- `take(&x)` 只用于有默认值的类型（可选值、数字、`String`、`Vec`、`Map`）；其他类型用 `replace(&x, 新值)` 或 `swap(&a, &b)`。
- 堆上的值用 `Box`，单线程共享用 `Rc`，跨线程共享用 `Arc`；图和树用 `Arena[T]` 加 `Id[T]`，Id 由“Arena 身份、槽位、代数”组成，用错 Arena 或用已删除的 Id 都能被发现。

**安全**

- 安全子集没有内存方面的未定义行为；`unsafe` 和 C 互操作要写明外部安全契约，并能被 `zhun audit` 列出，依赖里默认禁止。
- 整数溢出和越界默认 panic；需要回绕时写 `+%`、`-%`、`*%`。生成的 C 用 `__builtin_*_overflow` 检查溢出，并以 `-fwrapv` 编译。
- 移位、类型转换、指针运算在生成 C 时同样要避开 C 的未定义行为；从第一版 C 后端起就跑 AddressSanitizer、UndefinedBehaviorSanitizer 和差分测试。
- panic 直接终止进程，不跨线程或 C 边界展开栈；普通的函数退出照常执行确定性析构。涉及文件、事务、进程的逻辑要用 `T ! E` 显式处理错误，不能依赖 panic 时的清理。

**并发（v1）**

- 只有 OS 线程、`scope`、channel、`Mutex` 和原子类型，I/O 是阻塞式的。
- 一个值能否交给别的线程、能否被多个线程同时读，由编译器从类型结构推导；`Rc` 两者都不能，`Arc[T]` 只有在 `T` 可以被多线程共享时才能跨线程。
- 不做协程和 M:N 调度器，保持运行时小而且可移植。

## 工具链和运行时

编译器先生成 C，运行时分成“可移植核心”和“平台层”两层，三个桌面平台从第一天就一起支持。

&#91;embedded content: 编译流程和两层运行时 · 三套平台实现\]

读图：前端的检查结果以 JSON 返回给 agent；生成的 C 只和运行时打交道，换平台只需要换平台层的实现。

**运行时分两层**

- 可移植核心：字符串、容器、Unicode、panic 和各种检查，不包含任何系统头文件。
- 平台层：约 30 个函数的小接口，覆盖内存、文件、时间、随机数、线程、进程。v1 只有 POSIX（Linux、macOS 分别测试）和 Win32 两套实现；WASI 放到第二阶段。
- 生成的 C 只包含一个运行时头文件。

**目标平台**

- 第一阶段：Linux（x86-64、aarch64，musl 静态链接）、macOS、Windows（`x86_64-windows-gnu`）。Windows 从 P0 起就在真实的 Windows 机器上跑 CI，不只验证能生成。
- 以后：MSVC ABI、wasm32-wasi。macOS 的 SDK 和签名要求单独处理。
- 本机编译用系统的 C 编译器；交叉编译用固定版本的 `zig cc`。

**分发**

| 版本 | 内容 | 用途 |
| --- | --- | --- |
| Core | 编译器、标准库、预编译运行时 | 用本机 C 编译器，下载小 |
| Full | Core 加固定版本的 Zig 和各目标的 libc 支持 | agent、CI、交叉编译 |

`zhun toolchain install <目标>` 提前下载并校验工具链；`zhun build` 只用已安装的工具链，构建过程中从不联网。

**后端**

- 先生成 C，并输出 `#line` 指令，让报错能定位到源码行。
- 之后再考虑不依赖 C 编译器的直接后端（QBE 或 Cranelift）。

**产物和缓存**

- 项目目录里不产生中间文件；全局缓存按内容寻址，按字节上限和最近最少使用淘汰。
- 缓存键包含编译器版本、运行时版本、目标平台、编译参数和依赖内容的哈希。
- 调试信息默认分离，不做增量编译（编译本身要足够快）。
- 依赖用锁文件固定哈希，构建不执行构建脚本；依赖编译一次进共享缓存。

**编译器实现**

用 Rust 写，允许少量经过审计的第三方依赖（例如 JSON、哈希），不为了零依赖自己维护基础设施。

## 给 agent 的接口

编译器是 agent 的眼睛：每多一轮“编译、报错、修改”都是成本，所以诊断、查询和验证报告都要为机器设计。

**诊断**

- 输出 JSON：稳定的错误码、精确的位置、可机器应用的修复补丁。
- 修法要地道，不只是合法：移出 `Box` 或可选字段时建议 `take`，不是 `.clone()`。
- 借用类错误同时指出借用开始的位置和冲突的位置。
- 一次报全，不产生级联的假错误。
- lint（未使用的变量、导入）默认是警告，`zhun fix` 自动修复；CI 模式再升级为错误。

**查询命令**

| 命令 | 作用 |
| --- | --- |
| `zhun check --json` | 只做类型和所有权检查，不生成代码 |
| `zhun outline <包>` | 只输出签名，agent 不必读整份源码 |
| `zhun type-at <文件:行:列>` | 显示推导出的类型 |
| `zhun explain <错误码>` | 短说明加一个错误写法和一个正确写法 |
| `zhun doc <模块>` | 标准库文档，Markdown 输出，每个函数标明是否可能分配 |
| `zhun allocations <函数>` | 列出函数里可能堆分配的操作，用于排查性能 |
| `zhun fix` | 应用诊断里的修复补丁 |
| `zhun audit` | 列出 `unsafe`、C 互操作、关闭检查的位置 |
| `zhun verify --target <目标>` | 构建、测试、审计，输出结构化验证报告 |

**验证报告**

最终交付的不只是可执行文件，还有一份机器可读的报告，人据此决定是否接受。报告结构示例（是设计，不代表这些检查已经实现）：

```json
{
  "build": "success",
  "target": "x86_64-windows-gnu",
  "tests": { "passed": 128, "failed": 0 },
  "memory_safety": { "unsafe_blocks": 0, "sanitizer_failures": 0 },
  "dependencies": { "locked": true, "build_scripts_executed": 0 },
  "reproducible_build": true
}
```

`reproducible_build` 只能来自两次独立构建的逐字节比对；Sanitizer 通过也不等于证明了内存安全，报告不能夸大。

**速查卡**

一页规范，能整份放进模型的上下文；标准库最常用的入口（读输入、集合、排序、字符串）都写在里面。试点中 Gojo 查了约 6 轮文档，速查卡要把这类检索降到接近零。

## v1 范围与非目标

v1 只做满足四条硬性要求所必需的东西，其余推到第二阶段或交给包。

| 项目 | v1 | 说明 |
| --- | --- | --- |
| 所有权和借用检查，含局部视图集合和导出签名的来源标注 | 做 | 核心卖点 |
| C 后端，Linux、macOS、Windows（`x86_64-windows-gnu`） | 做 | 硬性要求 |
| 小标准库：io、fs、os、集合、字符串、时间、线程、测试 | 做 | 够写命令行工具和计算程序 |
| JSON 诊断、查询命令、`allocations` | 做 | agent 的主要接口 |
| 内置测试、`audit`、`verify` 验证报告 | 做 | 没人读代码时的防线 |
| Core 和 Full 两种分发，`toolchain install` | 做 | 交叉编译开箱即用，构建离线 |
| 契约（`requires`/`ensures`） | 第二阶段 | 先做运行时检查，静态证明更晚 |
| 能力系统（包声明能碰哪些资源） | 第二阶段 | 先做包级声明，不做效应推断 |
| WASI 平台层、MSVC ABI、直接后端 | 第二阶段 | 不影响前三条要求 |
| 编译期执行（comptime） | 不做 | 实现成本高，编译期错误对 agent 更难诊断 |
| async 和协程 | 不做 | 会让运行时变重、移植变难 |
| 视图存进普通字段 | 不做 | 多一套规则，就多一套没有训练数据的东西 |
| panic 栈展开 | 不做 | 跨平台展开机制成本高；panic 直接终止进程 |
| 包注册表 | 不做 | 先支持本地路径和 git 依赖 |
| 内建 HTTP、TLS | 不做 | 交给包 |

## 路线图与验收线

路线图按验收标准排，不按日期排：先打通三个平台的最小编译链路，再扩展语言功能；所有权规则在 P1 开工前冻结，因为它一旦在编译器实现后反复修改，会连带影响类型检查、标准库、C 代码生成和整个测试集。

1. **P0：最小垂直切片。** 编译器入口、最小语法、生成 C、POSIX 和 Win32 两套最小运行时。验收：Hello World 和整数计算在 Linux、macOS、Windows 真机上运行，Windows 进 CI。
2. **P1：类型、move、借用和 JSON 诊断。** 先冻结 `String`/`str`、`Vec`、`Map`、返回视图和 Arena 的所有权规则。验收：T01 到 T10 通过 `zhun check`，每个错误都带可应用的修复，诊断可复现。
3. **P2：`Box`、集合、字符串、错误处理。** 验收：T01 到 T10 在三个平台上实际运行通过。
4. **P3：并发、Arena、标准库、测试工具和 `verify`。** 验收：多文件项目和跨线程测试通过；一组“试图绕过检查”的对抗程序全部被拒绝。
5. **P4：agent 综合评测和性能测试。** 验收：达到下面预先冻结的晋级标准。

**正式实验设计**

| 对照组 | 目的 |
| --- | --- |
| Rust 1.99 系列，加 agent 速查卡和结构化诊断 | 判断现有语言加工具是否已经足够 |
| Gojo nightly | 判断简化的所有权模型是否降低开发成本 |
| Zhunsheng | 验证是否有额外优势 |

至少 30 道题，覆盖多文件程序、零拷贝解析、复杂数据结构、并发和 C 互操作；每道题随机化语言顺序，用多个模型各跑一遍，保存原始交互和编译日志，用隐藏测试判定正确性。

**晋级标准**

- 正确性：最终通过率不明显低于 Rust 对照组；内存安全测试没有未修复的漏判。
- 成本：正确性不退化的前提下，任务总成本（模型调用、编译、测试、修复）比 Rust 对照组低至少 20%，并经独立重复实验确认。

20% 是商业目标，不是已测出的收益。开始比较前，先用重复实验量出同一组内部的波动；如果波动接近 20%，要加大题量，否则分辨不出差异。不达标就优先改进 Rust 的 agent 工具层，而不是继续加语言功能。

**工程验收指标**

| 指标 | 目标 | 测法 |
| --- | --- | --- |
| 小程序编译耗时 | P50 不超过 200 ms | 固定硬件；分别测冷启动、热缓存、debug、release，记录 P50 和 P95 |
| 二进制，strip 后 | Linux 上不超过 250 KB | 按目标平台分别统计，统一 strip 和链接方式 |
| 运行性能 | 与 C 同量级 | 与 C、Rust、Gojo 用同一算法、同一数据布局比较 |
| 内存安全 | 无未修复漏判 | 对抗程序、随机生成程序、Sanitizer、差分测试 |
| Windows | 全部测试通过 | 在真实 Windows 机器上运行 |
| 构建可复现 | 两次构建逐字节一致 | 锁定工具链、依赖哈希、目标 ABI 和编译参数 |
| 项目目录清洁 | 0 个中间文件 | 构建后自动检查源码目录 |
| 每次构建新增字节 | 与 Rust 对照组比较 | 同一程序、同一构建模式 |
| agent 效率 | 达到晋级标准 | 完成率、尝试次数、token、成本、耗时、隐藏测试正确率 |

## 主要风险与待验证假设

最大的风险仍是冷启动：新语言没有训练数据，要到 P1 才能验证速查卡是否够用。

| 风险或假设 | 为什么是问题 | 怎么验证或缓解 |
| --- | --- | --- |
| 冷启动 | 模型对新语法没有先验；试点里 Gojo 的语法接近 Rust 和 Go，迁移几乎免费 | P1：只给速查卡，看能否写出并通过检查 |
| 借用检查的可靠性 | 没有生命周期标注的检查容易漏判，Gojo 为此写了 151 个对抗程序 | P3：对抗测试集、随机程序生成、Sanitizer |
| 证据偏薄 | 一个 agent、10 道小题，基线还是 Rust 1.75 | P4：30 道题、多个模型、随机顺序、Rust 1.99 |
| 差异化不足 | 结构化诊断、速查卡、审计也能做成 Rust 之上的工具层 | P4 把“Rust 加工具层”作为正式对照组 |
| 成本门槛分辨不出 | 同组重复实验的波动可能接近 20% | 先量波动，再定题量 |
| 返回视图的来源推断 | 私有函数的签名依赖函数体，改函数体可能让包内调用方报错 | 导出函数强制标注；在 P4 统计这类错误的占比 |
| panic 终止进程 | 测试里一次 panic 会杀掉整个测试进程；Windows 没有 fork | 每个测试放进单独的子进程，Windows 上用 spawn |
| C 后端的未定义行为 | 溢出、移位、类型转换处理不当，会在 C 层产生未定义行为 | 内建溢出检查、`-fwrapv`，Sanitizer 从第一版起跑 |
| 范围蔓延 | 调度器、网络协议、注册表都会拖慢核心 | 严格按“v1 范围与非目标”一节执行 |

还没有回答的问题：

- Zhunsheng 的商标核查，以及对不熟悉拼音的使用者是否好读好记。
- 许可证用 Apache-2.0 单许可，还是像 Rust 那样用 MIT 和 Apache-2.0 双许可？
- 速查卡第 8 节列出的几项语法选择。
