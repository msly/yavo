# Independent ASan/UBSan validation

This workflow tests the C generated by a specific Yavo source snapshot with an
independent GCC/Clang installation that has real AddressSanitizer and
UndefinedBehaviorSanitizer runtimes. It does not replace the pinned production
toolchain, change `toolchain.lock`, or turn pinned-toolchain `unsupported` results
into passes.

## Export on the compiler host

From the repository root, with Cargo and the project linker configured:

```sh
export PATH="$HOME/.cargo/bin:$PATH"
export CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_LINKER="$HOME/.yavo/bin/rust-linker"
perl tools/sanitizers/export.pl --out compiler/target/sanitizers-current/bundle.json
```

The exporter builds the release compiler, snapshots source inputs before/after,
and emits all `compiler/tests/p0/run_*.yv` and `panic_*.yv` programs to C. Exact
stdout and panic expectations come from their existing header comments. The JSON
bundle contains the generated C, entry sources, runtime header, their SHA-256
hashes, compiler executable identity, Git state, frontend/build receipts, and
repository input hashes. A change during export is an error.

Three existing fixtures print legitimate output not declared in their original
headers. `expectations.json` supplies the exact extra stdout/stderr, bound to each
fixture's source hash. Changed fixtures require an explicit expectation review;
the runner never learns expected output from the executable being tested.

To export chosen entries, repeat `--case relative/path/main.yv`. This also works
for multi-file project entries accepted by the compiler. Give each entry the
same `// expect-stdout:` / `// | text` or `// expect-panic:` header used by the P0
fixtures. Repository `.yv` inputs are hashed, including imported files; the
generated C must be self-contained apart from `yavo_rt.h`. External dependency
sources outside the repository require a separate provenance record and are not
covered by this exporter.

Use a fresh output path for every export. Transfer the bundle and validator to
the validation host without changing their bytes; record the transfer hashes.

## Execute on a Linux validation host

```sh
python3 tools/sanitizers/run.py bundle.json --cc gcc --jobs 2 --out validation-run
```

The output directory must not exist. Each artifact is built with separate
`-fsanitize=address` and `-fsanitize=undefined` flags, `-O1`, frame pointers, and
`YV_ALLOC_CHECK=1`. A clean allocation/free probe must pass. Deliberate use-after-
free and signed-overflow probes must each fail with their expected sanitizer
diagnostic before any application is accepted. A compiler accepting the flags
alone is insufficient.

Every program must match exact stdout, expected exit status, and either empty
stderr (or explicitly declared stderr) and its single named Yavo panic. Timeouts, signals, sanitizer output, extra
output, and compilation failures fail validation. There are no automatic
retries. Runs record the actual host, C compiler and runtime hashes, source/C/
binary hashes, process commands, durations, and complete output file hashes.
`report.json` is updated as programs finish and contains final pass/fail counts.

LeakSanitizer is disabled in this profile so it also works in ptrace-based
execution environments. Normal Yavo exits additionally require balanced runtime
heap-block counters; panic intentionally does not unwind. This is not a claim
that all leak classes are detected. TSan, Windows/macOS execution, and performance
measurements are separate checks.

Retain the bundle and complete output directory for review. Commit the report
and harness with the project; do not commit generated executables or large
temporary bundles. Re-export and rerun after compiler/runtime changes.
