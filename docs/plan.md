## 定位与目标

Yavo 是面向 agent 的原生系统语言：无 GC，靠所有权检查保证内存安全，性能接近 C，三个桌面平台从第一天起都能编译和运行。

产品目标：给定程序规格，agent 能以最低成本交付一个经过机器验证、可复现构建、满足目标平台约束的原生程序；人只批准规格和验收标准，不逐行读代码。

硬性要求有四条：

1. 无 GC。
2. 性能接近 C。
3. 跨平台编译方便，第一阶段就包含 Windows。
4. 使用者是 agent：代码由 AI 生成，人只写规格和看结果。

设计原则：

- **迭代轮数比打字成本重要。** 样板代码可以多，歧义不能多。
- **没人读代码，正确性靠机器验证。** 测试、审计和验证报告要内置。
- **没有训练数据。** 模型只能靠一页速查卡和编译器的反馈来学。
- **检查只看单个函数和签名。** 所有具名函数在签名里写明借用来源，改一处不会在远处引发错误。
- **语法不隐藏行为。** 没有白名单以外的隐式拷贝和控制转换，自动操作只有语义表第 8 节的封闭白名单；除集合字面量外，普通语法不引入堆分配，可能分配的标准库操作有成本说明。
- **安全规范以语义表为准。** 速查卡是从语义表提炼的简化写法，不能反过来充当规范。

## 依据

本规划是有依据的假设，不是定论：数据来自一个 agent、10 道 30 到 150 行的小题，在一台 Linux x86-64 沙箱里测得。

| 测量项 | Gojo（nightly 0.0.1-20261109） | Rust 1.75 |
| --- | --- | --- |
| 10 道题最终通过 | 10/10 | 10/10 |
| 一次通过 | 7/10 | 10/10 |
| 总尝试次数 | 14 | 10 |
| 编译通过后测试失败 | 0 次 | 0 次 |
| 编译耗时中位数 | 109 ms | 260 ms（波动大） |
| 二进制，strip 后中位数 | 约 200 KB | 约 390 到 430 KB |
| 项目目录内的中间产物 | 无 | cargo 零依赖时 13 到 16 MB |
| 带一个 regex 依赖时的产物 | 缓存多一个二进制大小的文件 | `target/` 50 到 104 MB |
| 工具链体积 | 编译器 4.7 MB | 约 294 MB |

Gojo 的 4 次失败全是编译失败：3 次来自所有权和视图模型，1 次来自“未使用变量即报错”。

关于这些数字的三点说明：

- Rust 是 apt 打包的版本，标准库自带调试信息，未 strip 的二进制有 13 MB，所以只比较 strip 后的大小。
- 每题先写 Gojo 后写 Rust，Rust 的一次通过率因此偏高；写题的 agent 对 Rust 和 Go 也有很强的先验。
- token 消耗没有测到，性能没有比较。

Windows 移植的测量：Gojo 生成的 C 可直接为 Windows 编译（0 个错误），但运行时拼成一个单元后有 464 个错误、15 个缺失头文件，集中在调度器、网络、子进程和内存映射。

v0.2 补充的三点：

- **Rust 基线需重新锁定。** 保留用户提供的 1.75 试点数据；旧文中的“当前稳定版 1.99.1”没有附可核验发布证据，本版不沿用这个时效性结论。正式实验锁定开测日经官方发布渠道核验的稳定版，记录 `rustc -Vv`、安装来源和工具链哈希；锁定后不随中途升级而变动。
- **“项目目录零产物”不是语言本身的优势。** Rust 用 `CARGO_TARGET_DIR` 也能把产物移出项目目录，但总量不变；真正可比的是“每次构建新增多少字节”，差异主要来自调试信息和依赖编译。
- **更正对 Gojo 的描述。** Gojo 允许局部的视图集合（`Vec[str]`、`Map[str, int]`）和 `view struct`，返回视图可以写 `-> str of a`；它禁止的是视图进入普通字段、`Box`、接口值和逃逸的闭包。v0.1 的速查卡比 Gojo 还严，而且与自己的 `fields()` 用法矛盾，v0.2 已改正。

## 取舍

只拿 Gojo 被实测验证过的优点，把它的短板从设计上避开。

| 做法 | 决定 | 理由 |
| --- | --- | --- |
| 无生命周期标注、单函数可检查的所有权模型 | 借鉴 | 小题上没有把 agent 卡死，错误集中在少数几类 |
| 局部视图集合（`Vec[str]`）、返回视图写明来源（`-> str of s`） | 借鉴（v0.2 新增） | 零拷贝解析不用复制字符串，视图又不会逃逸 |
| `?T` 取消 nil，`T ! E` 加 `try`/`catch` | 借鉴 | 编译通过的程序全部一次通过测试 |
| 编译成 C，生成代码只依赖一个小头文件 | 借鉴 | 生成的 C 可直接为 Windows 编译 |
| 用 `__builtin_*_overflow` 检查溢出，以 `-fwrapv` 编译 | 借鉴（v0.2 新增） | 溢出由内建函数检查；-fwrapv 只是加减乘的兜底，除法、移位、转换另有生成规则 |
| 编译约 100 ms、二进制约 200 KB、项目零产物 | 借鉴 | 实测数据 |
| 缓存保留最近 64 个二进制 | 改 | 64 个大程序可能占数 GB；改为按字节上限、最近最少使用淘汰 |
| 内置测试、种子可重放、`unsafe` 审计、从类型推导能否跨线程 | 借鉴 | 没人读代码时，这些是主要防线 |
| M:N 调度器、手写汇编、epoll | 不要 | Windows 移植的 464 个错误主要来自这里 |
| 借用持续到词法块结束 | 改 | T04 因此多花一次迭代，改为到最后一次使用为止 |
| 提示用 `.clone()` 修“移出 Box 字段” | 改 | 合法但会深拷贝；应按意图在 `take`、`.clone()` 和借用之间给出候选 |
| 未使用变量是编译错误 | 改 | 浪费一次编译往返，降为警告并可自动修复 |
| HTTP、TLS、YAML 进标准库核心 | 不要 | 推高实现和移植成本，放到包里 |
| 仓库没有许可证文件 | 避开 | 从第一天就用 Apache-2.0 |

## 语言设计

语法贴近 Rust 和 Go 的混合，让模型已有的知识能迁移。本节是概要：精确规则以“语义表”标签页为准，具体写法见速查卡。

**语法**

- 一件事只有一种写法，官方格式化工具只有一种风格。
- 没有宏、运算符重载、隐式转换；自动操作只有语义表第 8 节的封闭白名单。
- 声明顺序无关；`pub` 标记从包导出的函数和类型。
- 函数边界写显式类型，函数内可以推导。
- 有返回值的函数每条路径都写 `return`，不支持尾表达式返回；分支取值用 `=> 表达式` 的形式。

**类型**

- 结构体、带数据的枚举、接口、元组；泛型用单态化实现，可以用接口约束，统一用方括号，如 `Vec[T]`。
- 接口实现要显式声明，如 `struct Dog: Named`；泛型比较只通过内建的 `Eq`、`Ord` 协议。浮点数的 `==`、`<` 按 IEEE 754 计算，但浮点数不满足 `Eq`、`Ord`，排序用 `totalCmp`。
- `?T` 表示可能缺失，`T ! E` 表示可能失败，两者都必须处理。
- 接口值放进集合或字段时显式装箱：`Vec[Box[Named]]`。
- `String` 和 `str` 始终是合法的 UTF-8；系统给的参数、文件内容不是合法 UTF-8 时明确报错，不静默替换。

**内存模型**（语义表第 1 到 4 节）

- 按值赋值、放进集合、传给 `sink` 参数时，拥有值被移动；参数有三种模式：只读借用（默认）、`inout`（排他可变，调用处写 `&`）、`sink`（移入）。
- 借用类型公开为 `&T` 和 `&inout T`。`let`/`var` 只决定能否重新赋值，借用类型决定能否修改目标；`var` 不能把 `&T` 升级成 `&inout T`。
- `str`、`&T`、只读 `[]T` 复制的是描述符；`&inout T` 不可复制。v1 没有可变切片，修改元素用 `inout Vec[T]` 或元素的可变借用。`Vec[str]` 这类容器拥有自己的存储，元素携带外部借用。
- 携带借用的值可以做局部变量、参数和返回值，不能进入普通字段、`Box`、接口值、channel 或被保存的闭包；检查是递归的，证明不了就拒绝。
- 所有具名函数返回借用时写来源：`of a`、`of (a, b)`、`of self`、`of static`；泛型返回值可能携带借用时同样要写，例如 `-> ?T of xs`，实例化后不携带借用就不产生约束。来源是上界，只能指向借用参数或借用的接收者，不会延长拥有者的寿命；调用方只看签名。
- 普通函数不能通过 `inout` 参数往调用者的容器里写入新的借用。
- 借用持续到最后一次使用为止，禁止的是冲突访问。修改接收者的调用采用两阶段借用：实参可以读接收者（`v.push(v.len())` 合法），不能修改或移动它（2026-11-21 修订，原为不做两阶段借用）。
- 读取与匹配：集合和 Arena 的读取返回借用（`get` 得到 `?&V`，`getMut` 得到 `?&inout V`，`getCopy` 得到 `?V`）；`Map[String, V]` 的查询直接接受 `str`。匹配拥有的临时值（如 `ch.recv()` 的结果）可以移出其中的值；消费已有的可选变量写 `match take(&opt)`。
- 堆上的值用 `Box`，单线程共享用 `Rc`，跨线程共享用 `Arc`；图和树用 `Arena[T]` 加 `Id[T]`，Id 带有 Arena 身份。

**安全**（语义表第 6、7 节）

- 安全子集没有内存方面的未定义行为；`unsafe` 和 C 互操作要写明外部安全契约，能被 `yavo audit` 列出，依赖里默认禁止。
- 溢出、除零、最小整数除以 -1、越界移位、超出范围的转换都会 panic；每种运算都有独立的 C 生成规则和边界测试，`-fwrapv` 只是兜底。
- 从第一版 C 后端起就跑 AddressSanitizer、UndefinedBehaviorSanitizer 和差分测试。
- panic 和内存耗尽都直接终止进程，不展开栈；正常退出时按确定的顺序析构。

**并发（v1）**（语义表第 5 节）

- 只有 OS 线程、`scope`、channel、`Mutex` 和原子类型，I/O 是阻塞式的。
- 编译器推导 `Send` 和 `Sync`：`Arc[T]` 跨线程要求 `T` 两者都满足，`Arc[Mutex[T]]` 要求 `T: Send`；`Rc` 永远不能跨线程；接口值默认两者都不满足，`Box[Named + Send]` 只能转交给别的线程，不能被多个线程共享。
- 内建类型的契约由编译器规定，用户不能自行声明：通过 `Rc`、`Arc` 只能得到共享的只读访问，把句柄放进 `var` 也一样，要修改就用 `Mutex`；锁守卫不能移到别的线程，必须在取得锁的线程释放。
- 线程借用持续到线程确认结束；锁内借出的引用不能离开 `with` 块；channel 只传不携带借用的拥有值。
- 不做协程和 M:N 调度器，保持运行时小而且可移植。

编译器先生成 C，运行时分成“可移植核心”和“平台层”两层，三个桌面平台从第一天就一起支持。

读图：前端的检查结果以 JSON 返回给 agent；生成的 C 只和运行时打交道，换平台只需要换平台层的实现。

**运行时分两层**

- 可移植核心：字符串、容器、Unicode、panic 和各种检查，不包含 OS 专用头文件；允许 ISO C 的 `stdint.h`、`stddef.h`、`stdbool.h` 等基础头文件。
- 平台层：约 30 个函数的小接口，覆盖内存、文件、时间、随机数、线程、进程。v1 只有 POSIX（Linux、macOS 分别测试）和 Win32 两套实现；WASI 放到第二阶段。
- 生成的 C 只包含一个运行时头文件。

**目标平台**

- 第一阶段：Linux（x86-64、aarch64，musl 静态链接）、macOS、Windows（`x86_64-windows-gnu`）。Windows 从 P0 起就在真实的 Windows 机器上跑 CI；没有 Windows 运行环境时，Windows 测试在验证报告里记为“未执行”，不能算通过。
- 以后：MSVC ABI、wasm32-wasi。macOS 的 SDK 和签名要求单独处理。
- 发布构建和 `yavo verify` 只用锁定版本的完整工具链（固定版本的 Zig）。系统 C 编译器只是可选的本机开发模式，它的名字和版本写进构建清单和缓存键。
- 支持的独立 C 编译器下限设为 Clang 16、GCC 12；统一 C17。`zig cc` 作为完整工具链独立锁定，不靠推测其内嵌 Clang 版本放行。必要功能和参数须通过随包的能力探针；Apple Clang 按功能探针与 SDK 单独认证，不把版本数字直接等同于上游 Clang。具体策略见 `TOOLCHAIN-POLICY.json`。

**分发**

| 版本 | 内容 | 用途 |
| --- | --- | --- |
| Core | 编译器、标准库、预编译运行时 | 用本机 C 编译器，下载小 |
| Full | Core 加固定版本的 Zig 和各目标的 libc 支持 | agent、CI、交叉编译 |

`yavo toolchain install <目标>` 提前下载并校验工具链；`yavo build` 只用已安装的工具链，构建过程中从不联网。

**后端**

- 先生成 C，并输出 `#line` 指令，让报错能定位到源码行。
- 之后再考虑不依赖 C 编译器的直接后端（QBE 或 Cranelift）。

**产物和缓存**

- 项目目录里不产生中间文件；全局缓存按内容寻址，按字节上限和最近最少使用淘汰。
- 缓存键包含 Yavo 编译器与运行时内容哈希、实际 C 编译器/链接器的内容标识和版本、目标 ABI/CPU 特性、sysroot/SDK/libc 哈希、全部代码生成/链接参数、环境白名单、依赖源码和泛型实例化参数。仅版本字符串相同不能复用不明来源工具。预编译运行时按目标/模式/Sanitizer 配置分别缓存。
- 调试信息默认分离，不做增量编译（编译本身要足够快）。
- 依赖用锁文件固定哈希，构建不执行构建脚本；不含泛型的依赖产物按缓存键复用；泛型的单态化实例按具体类型另行缓存，不承诺所有泛型依赖只编译一次。

**编译器实现**

用 Rust 写，允许少量经过审计的第三方依赖（例如 JSON、哈希），不为了零依赖自己维护基础设施。

## 给 agent 的接口

编译器是 agent 的眼睛：每多一轮“编译、报错、修改”都是成本，所以诊断、查询和验证报告都要为机器设计。

**诊断**

- 输出 JSON：稳定的错误码、精确的位置、修复建议。
- 借用类错误同时指出借用开始的位置和冲突的位置。
- 一次报全，不产生级联的假错误。
- lint（未使用的变量、导入）默认是警告；CI 模式再升级为错误。
- 修复分三级。编译器不能只凭类型错误判断使用者想要哪种所有权语义，所以只有第一级会被自动应用：

| 级别 | 例子 | `yavo fix` 的行为 |
| --- | --- | --- |
| 可以证明不改变语义的机械修复 | 未使用的变量改名为 `_name`；补上缺少的导入；`v.push(v.len())` 这类编译器已证明安全的固定拆分模式（接收者是稳定的局部位置，被提前的是已知无副作用的读取） | 自动应用 |
| 会改变所有权、资源寿命、副作用顺序或程序行为 | 在 `take`、`.clone()`、改为借用之间选择；补写或修改 `of`；其他的实参拆分 | 列出候选补丁和各自的影响，不自动应用 |
| 意图不明，或没有局部修法 | 设计层面的借用冲突 | 只给诊断，不强行生成补丁 |

**查询命令**

| 命令 | 作用 |
| --- | --- |
| `yavo check --json` | 只做类型和所有权检查，不生成代码 |
| `yavo outline <包>` | 只输出签名，agent 不必读整份源码 |
| `yavo type-at <文件:行:列>` | 显示推导出的类型 |
| `yavo explain <错误码>` | 短说明加一个错误写法和一个正确写法 |
| `yavo doc <模块>` | 标准库文档，Markdown 输出，每个操作标明是否可能分配 |
| `yavo allocations <函数>` | 每个操作给出“已知不分配、可能分配、未知”之一，参数求值单独列出 |
| `yavo fix` | 只应用第一级修复 |
| `yavo audit` | 按应用、依赖、标准库、C 运行时分别列出 `unsafe`、C 互操作和关闭检查的位置 |
| `yavo verify --target <目标>` | 构建、测试、审计，输出验证报告 |

**验证报告**

每项检查都有状态：`passed`、`failed`、`not_run`、`unsupported`、`timeout`。只有全部必需检查都是 `passed`，报告总体才算通过。交叉编译成功不等于在该平台上测试过。下面的示例是交叉编译到 Windows，在 Linux 上跑了 Sanitizer，但没有 Windows 运行环境，所以总体结论是“未验证”：

```json
{
  "overall": "not_verified",
  "inputs": { "source": "sha256:…", "dependencies": "sha256:…", "toolchain": "sha256:…" },
  "checks": [
    { "name": "build", "target": "x86_64-windows-gnu", "artifact": "sha256:a1…", "ran_on": "x86_64-linux-gnu", "status": "passed" },
    { "name": "tests", "target": "x86_64-windows-gnu", "artifact": "sha256:a1…", "ran_on": null, "status": "not_run", "reason": "no Windows runner" },
    { "name": "sanitizers", "target": "x86_64-linux-gnu", "artifact": "sha256:b2…", "ran_on": "x86_64-linux-gnu", "status": "passed", "tools": ["address", "undefined"], "mode": "debug", "tests_run": 128 },
    { "name": "audit", "status": "passed", "scope": { "app": "audited", "dependencies": "audited", "stdlib": "audited", "c_runtime": "trusted_pinned" } },
    { "name": "reproducible_build", "target": "x86_64-windows-gnu", "status": "passed", "builds": 2, "cache": "bypassed", "artifacts": ["sha256:a1…", "sha256:a1…"] }
  ]
}
```

每项检查绑定自己的目标、工件哈希和实际运行平台。示例里 Windows 发布二进制（`a1`）和在 Linux 上跑 Sanitizer 的二进制（`b2`）是不同的工件；Linux 的结果只是辅助证据，不能填补 Windows 的测试状态。审计逐层写明范围：`audited` 是审计过，`trusted_pinned` 是作为锁定版本的受信组件接受、但没有审计，两者不能混成一个“通过”。可复现构建必须是两次绕过缓存的独立构建。Sanitizer 通过不等于证明了内存安全。报告结构是设计，这些检查还没有实现。

**工具验证配置**

`sanitize: address, thread` 表示必须分别构建/运行，不表示可把二者放进同一个 `-fsanitize`。默认内存配置为 ASan+UBSan，线程配置为 TSan，独立工件、独立状态；平台或 SDK 不支持时写 `unsupported`，不能当 passed。Linux 发布产物可以是 musl 静态链接，而 Sanitizer 专用验证配置使用经验证的动态 libc 工具链；两者的差异和哈希进入报告。验证报告不得把辅助工件当成目标发布工件。

规范库的公开签名、效果和来源见《标准库契约》；`yavo outline` / `doc` 必须从同一份签名数据库生成，避免另外维护相互矛盾的文字表。

**速查卡**

一页规范，能整份放进模型的上下文；标准库最常用的入口（读输入、集合、排序、字符串）都写在里面。试点中 Gojo 查了约 6 轮文档，速查卡要把这类检索降到接近零。

## v1 范围与非目标

v1 只做满足四条硬性要求所必需的东西，其余推到第二阶段或交给包。

| 项目 | v1 | 说明 |
| --- | --- | --- |
| 所有权和借用检查：局部视图集合、所有具名函数的 `of` 来源 | 做 | 核心卖点，规则见语义表 |
| C 后端，Linux、macOS、Windows（`x86_64-windows-gnu`） | 做 | 硬性要求 |
| 小标准库：io、fs、os、集合、字符串、时间、线程、测试 | 做 | 够写命令行工具和计算程序 |
| JSON 诊断、查询命令、`allocations` | 做 | agent 的主要接口 |
| 内置测试（带超时）、`audit`、`verify` 验证报告 | 做 | 没人读代码时的防线 |
| Core 和 Full 两种分发，`toolchain install` | 做 | 交叉编译开箱即用，构建离线 |
| 契约（`requires`/`ensures`） | 第二阶段 | 先做运行时检查，静态证明更晚 |
| 能力系统（包声明能碰哪些资源） | 第二阶段 | 先做包级声明，不做效应推断 |
| WASI 平台层、MSVC ABI、直接后端 | 第二阶段 | 不影响前三条要求 |
| 编译期执行（comptime） | 不做 | 实现成本高，编译期错误对 agent 更难诊断 |
| async 和协程 | 不做 | 会让运行时变重、移植变难 |
| 视图存进普通字段 | 不做 | 多一套规则，就多一套没有训练数据的东西 |
| 两阶段借用（`v.push(v.len())`） | 做（2026-11-21 修订；原为不做） | 接收者是变量或其字段时预留到实参求值结束；实参修改接收者仍报 E0403，候选修复为提前计算 |
| 元素上的修改方法（`v[i].push(x)`） | 做（2026-11-22，决定 17） | 先定位并可变借用元素，再求实参；实参使用该容器报 E0403（同 Rust），见语义表 V2a |
| 通过 `inout` 参数向调用者的容器写入新借用 | 不做 | 改为返回带 `of` 的结果 |
| 手写 `Send`、`Sync` | 不做 | 只由编译器推导 |
| panic 栈展开 | 不做 | 跨平台展开机制成本高；panic 直接终止进程 |
| 并发调度的确定性重放 | 不做 | 种子只重放随机输入和随机数序列 |
| 包注册表 | 不做 | 先支持本地路径和 git 依赖 |
| 内建 HTTP、TLS | 不做 | 交给包 |

## 路线图与验收线

路线图按验收标准排，不按日期排。P0 现在可以开工；P1 开工前先冻结“语义表”标签页，因为所有权规则一旦在编译器实现后反复修改，会连带影响类型检查、标准库、C 代码生成和整个测试集。

1. **P0：最小垂直切片。** 编译器入口、最小语法、生成 C、POSIX 和 Win32 两套最小运行时、锁定的工具链清单。验收：Hello World 和整数计算在 Linux、macOS、Windows 真机上运行，Windows 进 CI；按已定 C17/Clang 16/GCC 12 策略运行能力探针，生成实际工具链 lock 和平台证据；发布 Zig 的版本与哈希必须来自实际安装包。
2. **P1：冻结语义表，实现类型、move、借用和 JSON 诊断。** 使用 v0.5 已落盘的 check/fix 测试；诊断行号、修复候选和预期文件均从清单读取。验收：T01 到 T10 通过 `yavo check`；check 类和 fix 类测试全部符合预期；第一级修复能自动应用，其余错误给出候选补丁或诊断。
3. **P2：`Box`、集合、字符串、错误处理。** 验收：T01 到 T10 在三个平台上实际运行通过；run 类测试（数值、UTF-8、析构、所有权转移后的运行结果）全部通过。
4. **P3：并发、Arena、标准库、测试工具和 `verify`。** 验收：并发类和验证报告类测试全部符合预期；多文件项目和跨线程测试通过。
5. **P4：agent 综合评测和性能测试。** 验收：达到下面预先冻结的晋级标准。

对抗测试从 P1 开始：每引入一条所有权规则，就同时加入应通过和应拒绝的程序，因为检查器放行正确程序不代表它能拒绝危险程序。负例必须先能解析，再命中指定的错误码和位置；因语法错误被拒绝不算通过。测试运行器把每个测试放进单独的子进程并设置超时，超时后清理子进程；种子只保证随机输入和随机数序列能重放，不保证 OS 线程调度能重放。

**正式实验设计**

| 对照组 | 目的 |
| --- | --- |
| 开测前核验并锁定的 Rust stable，加 agent 速查卡和结构化诊断 | 判断现有语言加工具是否已经足够 |
| Gojo nightly | 判断简化的所有权模型是否降低开发成本 |
| Yavo | 验证是否有额外优势 |

至少 30 道题，覆盖多文件程序、零拷贝解析、复杂数据结构、并发和 C 互操作。每个“任务、模型、语言”组合都用全新的上下文，避免前一种语言已经解决了算法、后一种只是翻译；随机化语言顺序；用多个模型；保存原始交互和编译日志；用隐藏测试判定正确性；失败的任务同样计入成本和预算。

**晋级标准**（开测前冻结，测完不再调整）

- **正确性：** 以任务为单位配对，计算 Yavo 与 Rust 通过率之差 Δ；要求 Δ 的单侧 95% 置信区间下界不低于 −5 个百分点。同一道题用多个种子重跑时，统计上仍按任务分组，不能当成更多独立的题。内存安全测试没有未修复的漏判。
- **成本：** 单位成功交付成本 = 全部尝试的总成本（包括失败的任务）÷ 成功交付的任务数；要求比 Rust 对照组低至少 20%，并经独立重复实验确认。这样不会因为提前放弃部分任务而显得成本更低。
- **运行性能：** 对预先冻结的基准集合，每一项先算倍率：Yavo 耗时的中位数 ÷ C 耗时的中位数；要求各项倍率的几何平均不超过 1.5，同时列出每一项的倍率和最慢的项目。安全检查保持开启，编译模式、分配器和链接方式写进结果。

这三项是“值得继续投入”的门槛，不能用来宣称所有场景都已接近 C；20% 是商业目标，不是已测出的收益。题量要事先按统计功效算好：30 道题时一道题约等于 3.3 个百分点，远不足以证明 5 个百分点的非劣性。按正态近似粗算，假设两种语言约有 15% 的任务结果不一致、真实通过率相同，要让下界的点估计刚好达标约需 160 道题，要有 80% 的把握达标约需 370 道。实际题量用预实验测出的不一致比例重新计算。不达标就优先改进 Rust 的 agent 工具层，而不是继续加语言功能。

**工程验收指标**

| 指标 | 目标 | 测法 |
| --- | --- | --- |
| 小程序编译耗时 | P50 不超过 200 ms | 固定硬件；分别测冷启动、热缓存、debug、release，记录 P50 和 P95 |
| 二进制，strip 后 | Linux 上不超过 250 KB | 按目标平台分别统计，统一 strip 和链接方式 |
| 运行性能 | 各项倍率的几何平均不超过 1.5 | 与 C、Rust、Gojo 用同一算法、同一数据布局比较 |
| 内存安全 | 无未修复漏判 | 语义表测试集、随机生成程序、Sanitizer、差分测试 |
| Windows | 全部测试通过 | 在真实 Windows 机器上运行；没有时记为 `not_run` |
| 构建可复现 | 产物哈希一致 | 两次绕过缓存的独立构建；锁定工具链、依赖哈希、目标 ABI 和编译参数 |
| 项目目录清洁 | 0 个中间文件 | 构建后自动检查源码目录 |
| 每次构建新增字节 | 与 Rust 对照组比较 | 同一程序、同一构建模式 |
| agent 效率 | 达到晋级标准 | 完成率、尝试次数、token、成本、耗时、隐藏测试正确率 |

## 主要风险与待验证假设

最大的风险仍是冷启动：新语言没有训练数据，要到 P1 才能验证速查卡是否够用。

| 风险或假设 | 为什么是问题 | 怎么验证或缓解 |
| --- | --- | --- |
| 冷启动 | 模型对新语法没有先验；试点里 Gojo 的语法接近 Rust 和 Go，迁移几乎免费 | P1：只给速查卡，看能否写出并通过检查 |
| 语义缺口 | 已有功能组合起来时的行为没写清，实现编译器时会临时发明规则 | P1 前冻结语义表，每条规则配应通过和应拒绝的测试文件 |
| 借用检查的可靠性 | 没有生命周期标注的检查容易漏判，Gojo 为此写了 151 个对抗程序 | 对抗测试从 P1 开始，再加随机程序生成和 Sanitizer |
| 规则让常见写法变繁琐 | 所有具名函数都写 `of`；（2026-11-21：第三轮实验中“不做两阶段借用”造成 2/8 的失败，已改为两阶段借用） | 已证明安全的固定模式由 `yavo fix` 自动处理；P4 统计这类错误占多少迭代 |
| 显式可变遍历的适应成本 | `for x in xs` 只读；写入必须 `for x in &xs`，更少意外排他借用但多一种显式标记 | 规则本版固定；P1 回归测试覆盖两种遍历，P4 记录误写次数，开测后不改规则 |
| 证据偏薄 | 一个 agent、10 道小题，基线还是 Rust 1.75 | P4：多个模型、全新上下文、锁定的 Rust stable |
| 统计功效不足 | 30 道题证明不了 5 个百分点的非劣性 | 用预实验测出不一致比例，再按功效算题量 |
| 差异化不足 | 结构化诊断、速查卡、审计也能做成 Rust 之上的工具层 | P4 把“Rust 加工具层”作为正式对照组 |
| “看起来通过”的验证 | 工具没装、平台没测，或者检查的是另一个工件，报告也可能显示通过 | 每项检查绑定自己的工件和运行平台，`not_run` 不能算通过 |
| 测试被 panic 或死锁拖垮 | 一次 panic 会杀掉进程；死锁让测试永远不结束 | 每个测试单独子进程加超时，Windows 上用 spawn |
| C 后端的未定义行为 | 溢出、移位、转换处理不当，会在 C 层产生未定义行为 | 每种运算独立的生成规则和边界测试，Sanitizer 从第一版起跑 |
| 范围蔓延 | 调度器、网络协议、注册表都会拖慢核心 | 严格按“v1 范围与非目标”一节执行 |

实施时仍需取得的事实（不是未定语法）：

- P0：正式发行的 Zig 版本、下载内容哈希、SDK/CRT 哈希、三个真实平台的能力探针和运行回执。
- P4：预实验 60 道独立任务估计配对不一致率；正式任务不少于 400 道（q=0.15 时的规划下限），按功效公式和预实验的不一致率上界向上调整，在正式运行前锁定。没有预实验，不宣称题量已经有经验保证。
- 语法方向、遍历权限、库最小契约本轮已定，不继续保留并行选择。商标/正式发布名称审查独立于 P1，不在本轮断言完成。
