# 第 52 批：生成 C 与二进制体积归因

核对结论：第 41 批历史记录 **953,599 B C / 443,536 B Linux ELF**，第 51 批最终产物 **1,774,302 / 729,968 B**，增幅 **86.06% / 64.58%**。第 41 批的覆盖 88 后来已在第 42 批校正为同源码重建 **91/391**；比较覆盖时应保留这项校正。

证据：[详细数值与来源](../compiler/validation/batch52-codegen-size-2026-11-28.json)、`HANDOFF.md` 第 21–22 节、提交 `3ce5d36` 与 `76915bc`、第 51 批原始 `compiler/target/ci/selfhost-batch51-final/run-9_3vpthl/receipt.json`。

## 1. 样本与可比较范围

第 51 批使用服务器保留的最终 stage2 C/ELF 原产物。第 41 批本机没有找到原产物，按 `3ce5d36` 原始七个编译器模块重建历史 stage1，再由该历史编译器发射 C；C 后端使用该提交的 runtime、锁定 Zig 和同一 `-O2 -s -DYV_ALLOC_CHECK` 参数。重建为 **953,695 B C / 443,552 B ELF**，分别比历史记录多 96/16 B。

生成 C 会嵌入七个源文件路径及一次入口路径，共八处，全部逐字节写为四字符 `\ooo`；公共目录每增加一个字符，C 增加 `8 × 4 = 32 B`。96 B 正好对应三字符目录差。原始第 41 批路径未保留，不能据此声称原产物哈希已复现。下面的函数体归因排除路径表；ELF 表明确使用重建样本。

下表按真实 C 函数边界统计，源函数通过模块装载顺序映射回 Yavo 函数名；其余字节列入声明和路径表，合计可回到文件总字节数。

`runtime_source.header` 单函数为 **360,355 B**。独立 driver 需要在没有源码 checkout 时写出 runtime；被嵌入的头文件本身为 **89,063 B**，而 `cString` 把每个字节编码成 `\ooo`。整个 runtime 模块贡献 C 增量的 **43.9%**。单纯按已解锁语料数估计编译器体积，会遗漏独立 build/run、结构化诊断和源码身份带来的代码与数据。

源函数数从 **223 → 299**，生成 C 中 `t_N` 临时变量声明从 **13,703 → 20,054**。这些是文本级声明数量；C 后端会折叠、传播或删除其中一部分，不能将其数量等同于运行时分配或 ELF 体积。`codegen.yv` 的增量主要是实际新增函数和已有函数扩大，最大的非嵌入函数为 `methodValue` **45,100 B**、`emitStatement` **40,696 B**、`expressionValue` **29,304 B**。

## 3. 已找到的冗余及收益上限

所有字符串字面量在第 51 批 C 中占 **499,485 B**，解码后的载荷合计 **123,624 B**。其中 **2,711** 个全八进制字面量由现有 `cString` 形式产生，占 **499,198 B**。只读计算安全 ASCII 表示：普通可打印字符直接输出，双引号、反斜线、问号及换行/回车/TAB 必要转义，其余字节保持三位八进制；问号转义用于避免 C17 trigraph 改写。

| 只读估算 | 当前 | 安全 ASCII 表示 |
|---|---:|---:|
| 可转换字符串字面量 C 字节 | 499,198 | 131,850 |
| 总 C 字节 | 1,774,302 | 1,406,954 |
| **可减少 C 字节** | — | **367,348（20.70%）** |

此估算没有修改编译器或真实产物。转换后的字符串载荷相同，C 后端解析后仍是相同字节，**不能推算 ELF 同比减少 20.70%**。它能直接减少 C 文件、解析工作和归档体积；后续应单独测量后端耗时，再决定实现优先级。

从 `main` 出发，把直接调用及函数指针引用都计入静态可达关系，第 51 批有 **57 个不可达静态函数，22,111 B（1.25% C）**；第 41 批为 40 个、16,107 B。第 51 批只有三个属于 Yavo 源函数：`lexer.lexInto`、`lexer.lex`、`parser.parse`，其余主要是无条件生成的 clone/drop 帮助函数。删除这些生成文本的收益远小于字符串表示；`-O2` 已可删除静态不可达函数，不能再次把 C 字节当成可节省的 ELF 字节。后续可采用按需发射生命周期帮助函数，但仍需检查未调用函数以保持原有语言诊断。

## 4. ELF 增长落在哪里

| 文件区段 | 第 41 批重建 | 第 51 批原产物 | 增量 |
|---|---:|---:|---:|
| `.text` | 404,546 | 587,250 | +182,704 |
| `.rodata` | 22,461 | 121,928 | +99,467 |
| ELF 文件总字节 | 443,552 | 729,968 | +286,416 |

`.text` 和 `.rodata` 合计解释文件增量的 **98.5%**。只读数据的增长与新增 89,063 B runtime 嵌入相符；机器码增长来自语义检查/代码生成、普通 driver、诊断和摘要功能。没有证据把这次膨胀主要归因于重复生成未使用帮助函数。

下一次独立优化可先改 `cString` 的等价转义，验收采用 C 词法边界、NUL/高位字节/问号组合、固定点和三平台核心测试；此批只交归因与基线，不混入优化变更。
